## 3. El jail: el paso que falta en todas las notas anteriores

`boca-autojudge` **se niega a arrancar si no existe `/bocajail`**:

```bash
if [[ ! -e /bocajail ]]; then
  echo "Bocajail not found. Please run boca-createjail"
  exit 1
fi
```

Ninguna de las notas de abril menciona haber corrido `boca-createjail` en `boca-main`, y
efectivamente no existían ni `/bocajail`, ni `/home/bocajail`, ni el usuario `bocajail`, ni
`/etc/schroot/chroot.d/bocajail.conf`.

La explicación apareció más tarde en la sesión (ver §7): **el jail de abril estaba en
`boca-judge-1`, no en la main**, con fecha de creación 25/4 19:51–20:00 UTC, o sea **antes** del
primer run juzgado (20:13 UTC). Es decir que en abril el juzgado probablemente lo hizo el judge
dedicado, y en la main nunca hizo falta el jail. Hoy lo creamos igual en la main, porque queremos
poder juzgar en cualquiera de las dos arquitecturas.

### Qué hace `boca-createjail`

1. Crea el usuario `bocajail` con home en `/home/bocajail`.
2. Hace `ln -s /home/bocajail /bocajail` — **`/bocajail` es un symlink**, no un directorio.
3. Escribe `/etc/schroot/chroot.d/bocajail.conf`.
4. Corre `debootstrap` de la misma release de Ubuntu dentro de `/home/bocajail`.
5. Adentro del chroot: `apt-get update && upgrade`, y `apt-get install maratona-linguagens`
   (los compiladores).

**No es interactivo** (todos los `apt-get` llevan `-y`), pero **tarda entre 5 y 10 minutos** y
termina en ~1.6 GB. Conviene lanzarlo desatachado para que no lo corte una desconexión de SSH:

```bash
sudo bash -c 'nohup setsid boca-createjail > /tmp/createjail.log 2>&1 < /dev/null &'
# seguirlo con:
sudo tail -f /tmp/createjail.log
sudo du -sh /home/bocajail
```

> Hay que correrlo en **cada máquina que vaya a correr un autojudge**, incluida la main si el
> autojudge corre ahí.

### Gotcha: si se interrumpe, queda `/proc` montado y no se puede reintentar

Si `boca-createjail` se corta a mitad de camino, el `debootstrap` ya montó `/home/bocajail/proc`.
A partir de ahí:

- `rm -rf /home/bocajail` falla con `Operation not permitted` en todo `proc/<pid>/*`.
- Re-correr `boca-createjail` aborta con:
  `"You seem to have already installed /bocajail and the /bocajail/proc seems to be mounted.
  Please reboot the system to remove such mounted point"`.

El script te manda a reiniciar la VM, pero **no hace falta**. Alcanza con desmontar y limpiar:

```bash
sudo bash -c '
  for m in $(mount | grep -o "/home/bocajail[^ ]*" | sort -r); do
    umount "$m" 2>/dev/null || umount -l "$m"
  done
  rm -rf /home/bocajail
  rm -f /bocajail
  userdel -r bocajail 2>/dev/null
  rm -f /etc/schroot/chroot.d/bocajail.conf
'
```

Verificar que quedó limpio antes de reintentar:

```bash
mount | grep -i bocajail   # no debe devolver nada
id bocajail                # "no such user"
ls -d /bocajail /home/bocajail   # "No such file or directory"
```

Peor aún: un jail a medio construir es **más peligroso** que no tener jail, porque `/bocajail`
existe y `boca-autojudge` pasa su chequeo, arrancando contra un chroot incompleto.

### Verificar que el jail quedó bien

```bash
schroot -l    # debe listar chroot:bocajail
# Preguntar DENTRO del chroot, no desde el host:
for b in gcc g++ javac java kotlinc python3; do
  printf '%-9s %s\n' "$b" "$(sudo chroot /home/bocajail which $b 2>/dev/null || echo NO)"
done
sudo chroot /home/bocajail dpkg -l | grep maratona   # debe estar maratona-linguagens
```

> Chequear los binarios desde el host con `test -x /home/bocajail/usr/bin/javac` **da falsos
> negativos**: varios son symlinks a `/etc/alternatives/...`, que desde el host resuelven contra
> el root equivocado. Hay que preguntar adentro del chroot.

Con `maratona-linguagens 20230913` quedan disponibles `gcc`, `g++`, `javac`, `java` y `python3`.
**No** trae `kotlinc` ni `python2`.

Los errores de `dbus` y `E: Can not write log (Is /dev/pts mounted?)` en el log son **ruido
normal** de instalar paquetes dentro de un chroot; no indican falla.

### Gotcha: el autojudge NO es un servicio de systemd

No hay unit file: `systemctl is-enabled boca-autojudge` devuelve
`No such file or directory`. Es un script que hay que arrancar **a mano después de cada boot**:

```bash
sudo bash -c 'nohup setsid boca-autojudge > /tmp/autojudge.log 2>&1 < /dev/null &'
sudo tail -f /tmp/autojudge.log   # termina en "Nothing to do. Sleeping...."
```

Esto es lo que nos pasó hoy: la VM se había reiniciado y los envíos quedaban en `openrun` para
siempre, sin ningún error visible en la web. **Es el trap operativo número uno para el día del
contest.** Queda pendiente escribir una unit de systemd.

## 4. Paquetes `rbx` vs `box`: la extensión de C++

La advertencia de las notas de 2024 ("los nombres de las extensiones en la pestaña Languages
deben coincidir con las carpetas de los paquetes") es real, y acá está el detalle concreto:

| | C++ | C | Java | Kotlin | Python |
|---|---|---|---|---|---|
| Paquete **rbx** (B, de Mateo) | `cc` | `c` | `java` | `kt` | `py3` |
| Paquete **box** / `mpkg.py` (A, 2025) | `cpp` | `c` | `java` | `kt` | `py3` |
| **BOCA** `langtable` (default) | `cc` | `c` | `java` | — | `py3` + `py2` |

Las conclusiones importantes:

- **Con paquetes `rbx` no hay que tocar nada para C++**: `rbx` usa `cc`, que es exactamente el
  default de BOCA. Validado en vivo (ver §5).
- **Con paquetes `box`/`mpkg.py` C++ está roto**: el paquete trae `cpp` y BOCA busca `cc`. Si
  alguna vez se mezclan problemas del 2025 con los nuevos, esos no van a compilar. Se arregla o
  cambiando la extensión en BOCA, o cambiando `mpkg.py`.
- **Kotlin no se puede usar hoy**, por dos razones independientes: no está dado de alta en
  `langtable`, y `kotlinc` no se instala en el jail (`maratona-linguagens` no lo trae). Hay que
  resolver las dos cosas, no una.
- **Python 2 es una trampa**: está ofrecido en BOCA pero no hay intérprete en el jail y ningún
  paquete trae carpeta `py2`. Conviene borrarlo de `langtable`.

Detalle útil: BOCA **acepta** un archivo `.cpp` aunque la extensión del lenguaje sea `cc`, así
que el mismatch no se manifiesta al enviar (no da "name mismatch"), sino recién al juzgar.

### Cómo inspeccionar un paquete ya cargado

El paquete vive en la base como large object. Para ver qué carpetas trae realmente:

```bash
OID=$(sudo -u postgres psql -d bocadb -tAc \
  "select probleminputfile from problemtable where contestnumber=1 and problemnumber=2;")
sudo -u postgres psql -d bocadb -c "\lo_export $OID /tmp/pkg.zip"
sudo chmod 644 /tmp/pkg.zip
python3 -c "
import zipfile
n = zipfile.ZipFile('/tmp/pkg.zip').namelist()
for d in ('limits','run','compare','compile','tests'):
    print(d, sorted(x.split('/',1)[1] for x in n
          if x.startswith(d+'/') and x.count('/')==1 and not x.endswith('/')))
"
```

## 6. Recetas de diagnóstico (nombres de columnas de BOCA)

La base de BOCA tiene nombres poco obvios que cuestan tiempo si se adivinan. Los que importan:

| Lo que buscás | Dónde está |
|---|---|
| Problema de un run | `runtable.runproblem` (**no** `problemnumber`) |
| Texto del veredicto | `answertable.runanswer` (la columna, sí, se llama igual que la de runtable) |
| ¿Lo juzgó el autojudge (y no una persona)? | `runtable.autoanswer` / `autobegindate` / `autoenddate` no vacíos |
| Cuánto tardó en juzgarse | `autoenddate - autobegindate` (los rápidos dan 3–5 s) |
| Run sin juzgar | `runtable.runstatus = 'openrun'` |
| Paquete del problema | `problemtable.probleminputfile` (oid de large object) |

Dos columnas que **no** significan lo que parece:

- **`runtable.runjudge` no identifica al autojudge.** En los runs que vimos coincide con el
  `usernumber` del que envió (999 era el de `seba`, 5 el de `MateoCV`), así que es fácil creer que
  999 es un valor especial. No lo es.
- **`runtable.autoip` no identifica la máquina que juzgó.** Vale `local` incluso cuando juzgó una
  VM remota; ver §8. Para saber qué máquina juzgó, el log del autojudge es el único método
  confiable.

Ver `scripts/03-diagnose-boca.sh`, que junta todo esto en un solo comando.

Ojo con dos detalles al correr `psql` por SSH: hay que hacer `cd /tmp` antes (si no, `sudo -u
postgres` tira `could not change directory to "/home/<user>": Permission denied`, que es inocuo
pero ensucia la salida), y `$$` en una query se expande al PID del shell, así que conviene usar
`chr(65)` u otro recurso en lugar de comillas anidadas.

### Dos cosas que confunden al auditar el judge

**`/etc/boca.conf` dice `bdserver=localhost` y hay un Postgres local activo**, lo que hace
parecer que el judge apunta a su propia base. No es así: la config que realmente usa BOCA es
`/var/www/boca/src/private/conf.php`, y ahí el `dbhost` es correcto. El `bdserver` de
`/etc/boca.conf` sólo lo usa `boca-autojudge` para un sanity check. El Postgres local es un
sobrante de instalar el paquete `boca-db` y es inofensivo (su cluster **no tiene** `bocadb`).

**La regla de `iptables` que piden las notas no hace falta** en estas VMs: la política de `INPUT`
es `ACCEPT` sin reglas, y el tráfico interno del VPC ya lo habilita la regla
`default-allow-internal` de GCP. El paso está en las notas de 2023/2024 (venía de AWS) y quedó
copiado sin ser necesario.

### Cómo verificar que el judge realmente lee la base de la main

Tres chequeos independientes, sin depender de un envío:

```bash

# 2) Desde el judge: conexión establecida hacia la main
```

### Gotcha grande: el autojudge son DOS procesos, y `pkill -f boca-autojudge` no lo detiene

Esto costó una hora de confusión y una conclusión equivocada, así que vale la pena en detalle.

`boca-autojudge` es sólo un wrapper de bash que lanza un hijo `php autojudging.php`, y **el que
hace el trabajo real (compilar, correr, escribir el veredicto en la base) es el hijo `php`**:

```
33493  ppid=1      /bin/bash /usr/sbin/boca-autojudge     <- wrapper
33497  ppid=33493  php autojudging.php                    <- el que juzga
```

Consecuencia: si matás el wrapper, el hijo `php` **queda huérfano (reparentado a init) y sigue
juzgando indefinidamente**. Apagar el autojudge "a medias" es fácil y silencioso: `pgrep` del
wrapper no encuentra nada, uno cree que está apagado, y los envíos se siguen juzgando. Nos pasó
exactamente eso: se creyó estar probando el judge remoto cuando en realidad seguía juzgando un
`php` huérfano en la main, con 57 minutos de vida.

Para apagarlo de verdad hay que matar los dos, y **para consultarlo hay que mirar el hijo `php`**,
no el wrapper.

Además, los patrones tienen dos trampas encadenadas:

- **`pkill -f` se mata a sí mismo.** Matchea la línea de comandos completa, y el `bash -c` que
  ejecuta el comando contiene el string buscado. Mata su propio padre y la sesión SSH muere con
  `exited with return code [255]`, como si la VM se hubiera caído.
- **El truco del corchete (`boca-auto[j]udge`) no alcanza** si el script que hace la consulta
  menciona el nombre en otro lado (un `echo`, un comentario, un mensaje de ayuda). Ese texto sin
  corchetes sí matchea el patrón, y `pgrep -c` devuelve procesos que no existen. Pasó con
  `03-diagnose-boca.sh`, que reportaba 2 autojudges en una VM que tenía 0.

La forma robusta es `-x -f`, o sea match **exacto** de la línea de comandos completa, que nunca
coincide con la del script que pregunta:

```bash
# Consultar
sudo pgrep -x -f '/bin/bash /usr/sbin/boca-autojudge'   # wrapper
sudo pgrep -x -f 'php autojudging.php'                  # el que importa

# Apagar de verdad (los dos, en este orden)
sudo pkill -x -f '/bin/bash /usr/sbin/boca-autojudge'
sudo pkill -x -f 'php autojudging.php'
```

Ojo con no matar los `php-fpm` de Apache, que son otra cosa y hacen falta para la web. Los
patrones exactos de arriba no los tocan; un `pkill php` sí, y te deja el sitio caído.

### Validación del juzgado remoto, y por qué `autoip` no sirve para saber quién juzgó

Con el autojudge de la main **realmente** apagado (wrapper + `php`) y sólo el de `boca-judge-1`
corriendo, un envío en C++11 al problema B volvió `YES` en unos 4 segundos. Confirmado en el log
del judge:

```
Autojudging answered 1 '(YES)checker found no differences' (contest=1, site=1, run=257309906)
```

El hallazgo importante: **ese run quedó grabado en la base con `autoip = 'local'` aunque lo juzgó
una máquina remota.** O sea que `runtable.autoip` no identifica al juez y no sirve para auditar
qué máquina evaluó un envío; aparentemente es un literal que el autojudge escribe siempre igual.

Esto invalida un razonamiento que parecía sólido durante la sesión: los envíos de abril tenían
`autoip = 'local'`, y de ahí se dedujo que los había juzgado la main. Es falso: son perfectamente
compatibles con haber sido juzgados por `boca-judge-1`, que es lo que además indica la evidencia
del jail (la main no tenía jail en abril, así que no podía juzgar nada).

**Para saber qué máquina juzgó un run, el único método confiable es el log del autojudge**
(`/tmp/autojudge.log` si se arrancó como en §3), buscando el número de run:

```bash
sudo grep 257309906 /tmp/autojudge.log
```

Como el log vive en `/tmp` y se pierde con cada reboot, si hace falta trazabilidad post-contest
conviene escribirlo en un lugar persistente al arrancar el autojudge.

## 9. Arquitectura: la main no juzga

Queda fijado como decisión de diseño, no como accidente: **una main que corre web + base y no
juzga nunca, y N máquinas judge** que corren el autojudge y se conectan a la base de la main por
red. Juzgar es la parte que consume CPU, y no conviene que compita con el servidor web justo en el
momento en que todos los equipos están enviando.

Por eso `04-start-contest.sh` no tiene opción para levantar un autojudge en la main; al contrario,
verifica que no haya ninguno corriendo ahí y avisa si lo encuentra. Escalar es agregar judges:
`JUDGES="boca-judge-1 boca-judge-2" ./04-start-contest.sh`.

La main igual quedó con `/bocajail` creado (§3), de esta sesión, cuando todavía no estaba claro
que el judge de abril ya funcionaba. Es 1.6 GB de disco ya pago y sirve como respaldo manual de
emergencia, así que se dejó; pero en operación normal no se usa.
